## 1. Вердикт експерта

Застосунок функціональний і продуманий з точки зору UX-деталей: skeleton-лоадери, typewriter-ефект, undo-механізм видалення, фільтрація переглянутих фільмів, запам'ятовування налаштувань. Водночас присутні дві критичні вразливості: TMDB API-ключ вшитий у вихідний код і доступний будь-кому, а `innerHTML` у багатьох місцях приймає несанітизовані дані з API та користувацького вводу, що створює вектор XSS-атаки. `JSON.parse` з localStorage викликається без `try-catch`, що означає, що одне пошкоджене значення в сховищі зламає всю сторінку при завантаженні. Перевірка стану watched-панелі використовує неіснуючий клас `-translate-x-full`, що є прямою логічною помилкою. Послідовні (а не паралельні) запити до TMDB для кожного з 15 фільмів суттєво уповільнюють завантаження результатів.

### Фінальна п'ятірка
1. **Найважливіше, що варто змінити**: Санітизувати всі дані перед вставкою через `innerHTML`, або перейти на `textContent`/DOM API для даних, що надходять із зовнішніх джерел (API, localStorage, користувацький ввід).
2. **Найважливіше, що варто побудувати**: Захисний шар навколо `localStorage` — обгортку з `try-catch` та валідацією схеми даних при зчитуванні, щоб пошкоджені дані не крашили сторінку.
3. **Найважливіше, що варто прибрати**: Хардкоджений TMDB API-ключ із вихідного коду — або перенести виклики TMDB через мінімальний backend/proxy, або зробити його ключем, який користувач надає сам.
4. **Найважливіше, що варто перевірити експериментом, перш ніж будувати**: Паралельні запити до TMDB (замість послідовних) — виміряти реальний час завантаження і переконатися, що TMDB не блокує burst-запити.
5. **Найважливіше, у чому ми, можливо, досі помиляємось**: Ми припускаємо, що Gemini стабільно повертає валідний JSON із правильними назвами фільмів — реальні відповіді ШІ можуть містити галюцинації (неіснуючі фільми), і масштаб цієї проблеми без runtime-тестування невідомий.

## 3. Детальні знахідки

### [AUD-001] XSS через innerHTML з несанітизованими даними
- **Тип**: `Risk`
- **Серйозність**: `Critical`
- **Впевненість**: `ПІДТВЕРДЖЕНО`
- **Локація**: `index.html:458`, `index.html:522`, `index.html:910`, `index.html:998`, `index.html:1228`
- **Суть проблеми**: У багатьох місцях коду дані з зовнішніх джерел (TMDB API, Gemini API, повідомлення про помилки) вставляються в DOM через `innerHTML` без будь-якої санітизації. Наприклад:
  - Рядок 458: `toast.innerHTML = \`<span>${message}</span>\`` — якщо `message` містить HTML, він буде виконаний.
  - Рядок 522: `${m.title_ua}` — назва фільму з TMDB або localStorage.
  - Рядок 998: `${plot}` — опис сюжету фільму вставляється як-є.
  - Рядок 1228: `${err.message}` — повідомлення про помилку з мережевого запиту.
- **Пояснення терміна**: XSS (Cross-Site Scripting) — атака, при якій зловмисний JavaScript-код потрапляє на сторінку через дані і виконується в браузері жертви, маючи доступ до всіх її даних на цій сторінці.
- **Чому це важливо на практиці**: Якщо TMDB API поверне назву фільму з HTML-тегами (або зловмисник модифікує дані в localStorage), цей HTML буде виконаний у контексті сторінки. Зловмисний скрипт зможе вкрасти Gemini API-ключ із localStorage.
- **Як відтворити**: Вручну додати до localStorage (`ani_movie_favorites`) фільм з `title_ua: "<img src=x onerror=alert(document.cookie)>"`, потім відкрити панель обраних.
- **Рекомендоване виправлення**: Створити функцію-санітайзер `escapeHtml(str)` яка замінює `<`, `>`, `"`, `'`, `&` на HTML-ентітети. Застосувати її до всіх змінних, що потрапляють в `innerHTML`. Або використовувати `textContent` / DOM API (`createElement` + `textContent`) для вставки текстового контенту.
- **Оцінка складності**: `Години` — потрібно переглянути кожне місце вставки.

### [AUD-002] TMDB API-ключ вшитий у вихідний код
- **Тип**: `Risk`
- **Серйозність**: `Critical`
- **Впевненість**: `ПІДТВЕРДЖЕНО`
- **Локація**: `index.html:381`
- **Суть проблеми**: `const TMDB_KEY = "3a61a409418b83fcb020683e206ae889"` — API-ключ TMDB жорстко прописаний у JavaScript і видимий будь-кому, хто відкриє сторінку або перегляне вихідний код.
- **Пояснення терміна**: Хардкоджений ключ (hardcoded key) — це секретний ідентифікатор, записаний напряму в код замість того, щоб бути захованим на сервері; будь-хто може його побачити і використати.
- **Чому це важливо на практиці**: Будь-хто може використати цей ключ для власних запитів до TMDB API від вашого імені. Якщо квота буде вичерпана або ключ забанять за зловживання, ваш застосунок перестане працювати. TMDB має ліміти і може відкликати ключ.
- **Рекомендоване виправлення**: Для персонального проєкту, який не деплоїться публічно, це прийнятний компроміс. Для публічного деплою — перенести TMDB-запити на мінімальний серверний проксі (Cloudflare Worker, Vercel Edge Function), або зробити TMDB-ключ користувацьким (аналогічно Gemini-ключу).
- **Оцінка складності**: `Години` — якщо через проксі.

### [AUD-003] Gemini API-ключ передається в URL query string
- **Тип**: `Risk`
- **Серйозність**: `High`
- **Впевненість**: `ПІДТВЕРДЖЕНО`
- **Локація**: `index.html:782`
- **Суть проблеми**: URL формується як `...generateContent?key=${CURRENT_API_KEY}`. API-ключ потрапляє в URL, який зберігається в історії браузера, може бути зафіксований проксі-серверами, з'явитися в логах мережевого обладнання та в HTTP-заголовку `Referer`.
- **Пояснення терміна**: Query string — це частина URL після знаку `?`. Дані в ній видимі всім посередникам між вашим браузером і сервером (проксі, роутери, CDN).
- **Чому це важливо на практиці**: Gemini API-ключ дає доступ до Google AI Studio, і його витік може призвести до фінансових витрат на акаунті Google Cloud власника ключа.
- **Рекомендоване виправлення**: Це обмеження самого Gemini REST API — ключ передається саме через query parameter. Для підвищення захисту: (а) використовувати API-ключ з обмеженнями по IP/referer у Google Cloud Console, (б) або обгорнути виклики серверним проксі, що додає ключ на стороні серверу.
- **Оцінка складності**: `Години`

### [AUD-004] JSON.parse з localStorage без try-catch
- **Тип**: `Bug`
- **Серйозність**: `High`
- **Впевненість**: `ПІДТВЕРДЖЕНО`
- **Локація**: `index.html:427-428`, `index.html:922`
- **Суть проблеми**: Три виклики `JSON.parse(localStorage.getItem(...))` виконуються без `try-catch`:
  ```js
  let favorites = JSON.parse(localStorage.getItem('ani_movie_favorites')) || [];   // рядок 427
  let watchedMovies = JSON.parse(localStorage.getItem('ani_movie_watched')) || []; // рядок 428
  const savedResults = JSON.parse(localStorage.getItem('ani_last_results')) || []; // рядок 922
  ```
  Якщо значення в localStorage пошкоджене (не валідний JSON), `JSON.parse` викине виключення, і вся сторінка перестане працювати — решта JavaScript не виконається.
- **Пояснення терміна**: `JSON.parse` — функція, яка перетворює текстовий рядок у JavaScript-об'єкт; якщо рядок має невалідний формат, функція крашить виконання з помилкою.
- **Чому це важливо на практиці**: Пошкодження localStorage може статися через повне заповнення сховища (QuotaExceededError при попередньому записі), через ручне редагування через DevTools, або через інше розширення браузера.
- **Як відтворити**: Відкрити DevTools → Application → Local Storage → встановити `ani_movie_favorites` у значення `{invalid json`. Перезавантажити сторінку — вона зламається.
- **Рекомендоване виправлення**: Обгорнути кожен `JSON.parse` в `try-catch` з фолбеком на порожній масив:
  ```js
  function safeParseJSON(key, fallback = []) {
      try { return JSON.parse(localStorage.getItem(key)) || fallback; }
      catch { return fallback; }
  }
  ```
- **Оцінка складності**: `Хвилини`

### [AUD-005] Помилковий клас `-translate-x-full` у перевірці watched-панелі
- **Тип**: `Bug`
- **Серйозність**: `Medium`
- **Впевненість**: `ПІДТВЕРДЖЕНО`
- **Локація**: `index.html:587`
- **Суть проблеми**: Після виклику `toggleWatched()` перевірка стану панелі використовує клас `-translate-x-full` (зі знаком мінус):
  ```js
  if(!document.getElementById('watchedPanel').classList.contains('-translate-x-full')) renderWatchedList();
  ```
  Але панель використовує клас `translate-x-full` (без мінусу, рядок 257). Клас `-translate-x-full` ніколи не присвоюється, тому `.contains('-translate-x-full')` завжди повертає `false`, і `renderWatchedList()` викликається **завжди**, навіть коли панель закрита і результат ніхто не бачить.
- **Пояснення терміна**: Tailwind CSS клас `translate-x-full` зміщує елемент вправо на 100% ширини (приховує його); `-translate-x-full` (зі знаком мінус) зміщує вліво — це зовсім інший клас.
- **Чому це важливо на практиці**: Кожного разу при натисканні кнопки "Переглянуто" (навіть із закритою панеллю) виконується зайвий рендеринг HTML-списку, що марно витрачає ресурси. Порівняйте з коректною перевіркою для панелі обраних на рядку 504.
- **Рекомендоване виправлення**: Замінити `-translate-x-full` на `translate-x-full`.
- **Оцінка складності**: `Хвилини`

### [AUD-006] Одна глобальна змінна lastRemovedFavorite — undo зламаний при швидкому видаленні
- **Тип**: `Risk`
- **Серйозність**: `Medium`
- **Впевненість**: `ПІДТВЕРДЖЕНО`
- **Локація**: `index.html:434`, `index.html:530-554`
- **Суть проблеми**: Змінна `lastRemovedFavorite` — єдина на всю сторінку. Якщо користувач швидко видалить два фільми з обраного (протягом 4 секунд — часу життя тосту), друге видалення перезапише `lastRemovedFavorite`, і натискання "Скасувати" на першому тості відновить другий фільм замість першого.
- **Пояснення терміна**: Race condition — ситуація, коли результат залежить від порядку/швидкості дій, які не синхронізовані між собою.
- **Чому це важливо на практиці**: Користувач втратить один фільм з обраного без можливості відновлення.
- **Рекомендоване виправлення**: Передавати об'єкт видаленого фільму безпосередньо в замикання (closure) callback-функції undo, замість збереження в глобальній змінній:
  ```js
  const removedMovie = existingFavorites[removedIndex];
  showToast("🗑️ Фільм видалено", () => {
      favorites.push(removedMovie);
      // ...
  });
  ```
- **Оцінка складності**: `Хвилини`

- **Впевненість**: `ПІДТВЕРДЖЕНО`

- **Суть проблеми**: Після отримання списку фільмів від Gemini, для кожного фільму робиться два послідовних запити до TMDB (пошук + деталі): `await fetch(search)` → `await fetch(details)`. Для 15 фільмів це до 30 послідовних HTTP-запитів. Кожен чекає завершення попереднього.
- **Пояснення терміна**: Послідовні запити (sequential requests) — це коли кожен наступний запит починається лише після завершення попереднього, замість того щоб запускати декілька паралельно.
- **Чому це важливо на практиці**: При середньому RTT 200-300мс до TMDB API, 30 послідовних запитів можуть зайняти 6-9 секунд тільки на мережеву затримку, не рахуючи часу Gemini.
- **Рекомендоване виправлення**: Використати `Promise.allSettled()` для паралельного виконання запитів пачками (по 4-5 одночасно), щоб не перевантажити TMDB rate limit.
- **Оцінка складності**: `Години`

### [AUD-009] Нерозділена подвійна ідентичність фільмів (TMDB id vs imdbID)
- **Тип**: `Risk`
- **Серйозність**: `Medium`
- **Впевненість**: `ПІДТВЕРДЖЕНО`
- **Локація**: `index.html:489-490`, `index.html:517`, `index.html:569-570`
- **Суть проблеми**: Скрізь у коді ідентифікатор фільму визначається як `m.id || m.imdbID`. Це означає, що система підтримує два різних формати ідентифікаторів без чіткого розмежування. TMDB `id` — це число (наприклад, `550`), а `imdbID` — рядок (наприклад, `"tt0137523"`). Порівняння через `==` (нестрогу рівність, рядки 570, 595, 930-931) маскує цю невідповідність, але це крихке рішення.
- **Пояснення терміна**: Подвійна ідентичність — це коли один об'єкт може ідентифікуватися двома різними ключами різних типів, і система не знає точно, який саме використовувати.
- **Чому це важливо на практиці**: Якщо фільм збережений в обране з `imdbID` (з давніших версій коду або іншого джерела), а потім його шукають за TMDB `id` — він не знайдеться у списку, і користувач побачить дублікат.
- **Рекомендоване виправлення**: Стандартизувати: завжди використовувати TMDB `id` як єдиний ідентифікатор. При зчитуванні старих даних із localStorage — нормалізувати до TMDB id.
- **Оцінка складності**: `Години`

### [AUD-012] @import у \<style\> блокує рендеринг
- **Тип**: `Debt`
- **Серйозність**: `Low`
- **Впевненість**: `ПІДТВЕРДЖЕНО`

## 5. Аудит неявних припущень

- **Припущення 1**: Gemini API завжди повертає валідний JSON з правильною структурою `[{title_en, title_ua, plot}]`.
  - **Статус**: `[СУМНІВНЕ]`
  - **Загроза**: Якщо Gemini поверне невалідний JSON або об'єкти з відсутніми полями, `JSON.parse` крашне (обробляється catch на рядку 1135), але відсутні поля (`title_en = undefined`) призведуть до помилок пошуку в TMDB.
  - **Контрприклад**: Gemini може повернути JSON обгорнутий у markdown-блок (\`\`\`json...\`\`\`), або додати коментар перед масивом. Спроба контрприкладу: ймовірна проблема — `responseMimeType: "application/json"` у generationConfig частково захищає від цього, примушуючи модель відповідати саме JSON.

- **Припущення 2**: Назва фільму `title_en` від Gemini завжди знаходиться в TMDB через пошук.
  - **Статус**: `[СУМНІВНЕ]`
  - **Загроза**: Gemini може галюцинувати — назвати неіснуючий фільм, або дати неточну назву, яка не знайдеться пошуком TMDB. У такому випадку фільм тихо пропускається (рядок 1157), і якщо пропущено багато — користувач побачить менше 8 карток.

- **Припущення 3**: TMDB API завжди доступний і відповідає без помилок.
  - **Статус**: `[СУМНІВНЕ]`
  - **Загроза**: TMDB rate limit — 40 запитів за 10 секунд. При 30 послідовних запитах (15 пошуків + 15 деталей) це може бути перевищено, що призведе до відмов API. Проте `fetchWithRetry` обробляє 429 з backoff.

- **Припущення 4**: localStorage завжди доступний і не заповнений.
  - **Статус**: `[СУМНІВНЕ]`
  - **Загроза**: У приватному режимі Safari localStorage має обмеження, і `setItem` може кинути виключення. Код не обробляє `QuotaExceededError`. Спроба контрприкладу: відкрити у Safari Private Mode → додати багато фільмів — не перевірено.

- **Припущення 5**: Всі TMDB ID є числами, а не рядками.
  - **Статус**: `[ПІДТВЕРДЖЕНО КОДОМ]` — TMDB API завжди повертає числові ID.
  - **Загроза**: Мінімальна, але при серіалізації/десеріалізації через JSON тип зберігається.

### Domain Model Challenge
Застосовано. Концептуальна модель застосунку (Gemini → пошук TMDB → рендер карток) загалом відповідає реальній задачі — рекомендувати фільми за настроєм. Однак є одне суттєве спрощення: Gemini генерує `title_en` (англійську назву), і за нею шукається фільм у TMDB. Якщо Gemini назве фільм трохи інакше ніж TMDB (наприклад, "The Lord of the Rings: The Fellowship of the Ring" vs "Lord of the Rings: Fellowship of the Ring"), пошук може знайти не той фільм або не знайти нічого. Доменно коректнішим було б попросити Gemini повертати TMDB ID напряму, але модель їх не знає достовірно — тому поточний підхід (пошук за назвою) є розумним компромісом.

### 6.1 Відсутня інфраструктура
- [x] **[Feature] Структуроване логування**: Помилки виводяться тільки в `console.error` без контексту. Для персонального проєкту це прийнятно.
- [ ] **[Concept] Версіонування даних localStorage**: Якщо структура збережених даних зміниться (додасться нове поле), старі записи стануть невалідними. Немає міграцій.
- [ ] **[Guarantee] Офлайн-стійкість**: Повна залежність від мережі. При відсутності інтернету — білий екран без пояснення.
- [ ] **[Feature] Довідка для користувача**: Немає пояснення, що таке API Key і як його отримати (є лише посилання).
- [x] **[Feature] Експорт результатів**: Для цього типу застосунку (вибір фільму на вечір) експорт не потрібен.
- [x] **[Guarantee] Фізична правдоподібність**: N/A — немає розрахунків.

### Foundation & Kludge-Stack Pattern (2.3)
Застосовано. Кludge-stack pattern **не виявлено**. Код має окремі недоліки, але жоден з них не є наслідком зламаного фундаментального рішення, яке компенсується ланцюгом workaround-ів.

### Counterexample Hunt

### Transformation search

### 6.2 Обґрунтовані ідеї розвитку

1. **[Opportunity] Паралельні запити до TMDB**:
   - *Що зробити*: Замінити послідовний цикл `for...await` на паралельні запити через `Promise.allSettled()` з обмеженням конкурентності (concurrency limit) до 4-5 одночасних запитів.
   - *З чого випливає*: AUD-007 (послідовні мережеві запити).
   - *Практична користь*: Value: high, Confidence: high. Скорочення часу завантаження результатів приблизно у 3-5 разів.

2. **[Opportunity] Захисна обгортка localStorage**:
   - *Що зробити*: Модуль `storage.js` з функціями `safeGet(key, fallback)`, `safeSet(key, value)` що обгортають JSON.parse/stringify у try-catch і обробляють QuotaExceededError.
   - *З чого випливає*: AUD-004, припущення 4.
   - *Практична користь*: Value: high, Confidence: high. Запобігає повному крашу сторінки.

3. **[Opportunity] Обробник Escape для модалок + focus trap**:
   - *Що зробити*: Глобальний keydown-обробник для Escape; при відкритті модалки — переміщати фокус всередину і обмежувати Tab-навігацію елементами модалки.
   - *З чого випливає*: AUD-016.
   - *Практична користь*: Value: medium, Confidence: high.

4. **[Експеримент] Валідація відповіді Gemini через JSON Schema**:
   - *Що зробити*: Перед обробкою масиву фільмів від Gemini — перевірити, що кожен елемент має обов'язкові поля `title_en`, `title_ua`. Відфільтрувати невалідні.
   - *З чого випливає*: Припущення 1 (Gemini завжди повертає правильну структуру).
   - *План експерименту*: Зробити 20 різних запитів до Gemini і подивитися, скільки разів відповідь не відповідає очікуваній структурі. Якщо >10% — впроваджувати валідацію.

5. **[Opportunity] Нормалізація ідентифікаторів фільмів**:
   - *Що зробити*: Стандартизувати: всюди використовувати тільки `id` (TMDB числовий), прибрати всі `m.id || m.imdbID` конструкції.
   - *З чого випливає*: AUD-009.
   - *Практична користь*: Value: medium, Confidence: high. Усуває цілий клас потенційних багів.

### 6.3 Розглянуто і свідомо відхилено
- **Перенесення на React/Vue фреймворк**: Відхилено — для одного файлу в 1235 рядків переїзд на фреймворк створить більше інфраструктурного оверхеду, ніж вирішить проблем. Vanilla JS достатній для цього масштабу.
- **Server-Side Rendering**: Відхилено — застосунок повністю клієнтський за дизайном, SSR не додасть цінності.
- **Інтернаціоналізація (i18n)**: Відхилено — персональний проєкт для конкретної людини, мова UI не потребує перемикання.
